# 教授報告與講稿製作流程

- 記憶 ID：`professor-report-workflow`
- 最後確認：2026-09-14
- 依據：使用者在本次報告製作中的明確要求與修正，整理為可沿用的流程，不保存對話逐字稿。
- 適用：教授報告、研究週報、累積補報、口頭講稿、HTML，以及要求「繼續」或改寫既有報告的任務。
- 成果範例：[2026-09-14 第一人稱累積研究報告](../../../school/docs/reports/professor_catchup_report_2026-09-14_zh.html)。這是格式與敘事範例，不是未來研究狀態的依據。

## 一、已確認的使用者要求

1. **以使用者為主角，用第一人稱敘述。** 正文和講稿都用「我遇到……」「我查到……」「我選擇……」「我嘗試……」「我目前能支持……」。不是助手向使用者提供「你可以怎麼報告」的建議稿。
2. **交付 HTML 成品。** 不只在對話中列大綱；沿用既有報告並實際更新檔案，提供可點開的連結。
3. **前幾次沒有報告時，要做累積補報。** 不限於今天或本週的新結果；以研究脈絡涵蓋先前尚未口頭報告的工作。不能因為已有週報檔案，就認定教授聽過。
4. **我遇到的問題也要報告。** 保留研究動機、困難、排查、處理、結果與限制，不能只留下漂亮數字。
5. **尋找能模擬環境的 API／平台的過程要報告。** 說明需求從何而來、在哪些來源找到候選、如何比較、為何選擇或排除，以及實際串接和驗證到了哪一步。
6. **製作流程放進 ResearchWorkspace 專案資料。** 不只留在對話、個人記憶或可重建快取。

先前的教授受眾限制仍適用：排除與研究無關的個人開發、工作區維護及投稿事務。2026-09-14 的明確補充是：**直接影響研究可行性或證據解讀的技術問題與探索過程必須納入**，不能一概當成工程細節刪除。

## 二、開始前：找回真正要續作的報告

1. 確認本次是新報告、累積補報、續作，還是只調整口吻／版面。續作時先讀既有成品與尚未完成項目，不重做已確認的內容。
2. 分開記錄「報告日期」「證據產生日期」「實際涵蓋期間」。今天整理舊結果，不代表今天完成新實驗。
3. 若使用者明確說先前沒有報告，就採累積敘事；若未交代口頭報告紀錄，不自行宣稱哪些內容已向教授報告。
4. 沿用使用者指定或現有報告的時長；沒有時長時可先做短版摘要與可展開細節。範例約 15 分鐘，不是固定時長要求。
5. 先讀 canonical thesis repository 的適用指引與來源。ResearchWorkspace 管理流程、索引、出處及驗證；研究報告仍存於 thesis repository。

## 三、取證：先對齊來源，再寫敘事

1. 依 ResearchWorkspace Intelligence 流程，以 resolve、orchestration plan、matching-audience context pack 縮小研究範圍，再讀原始來源。本文件需另外明確讀取，不假設 Context Pack 已包含。
2. 對講稿流程這類非研究主張任務，若 graph resolver 只有零分 fallback，不把推薦 topic 當作內容證據，也不因此擴張為方法或實驗修改。
3. 在 canonical checkout 先做唯讀狀態檢查：HEAD、工作樹、remote-tracking 狀態及來源日期。保留既有未提交修改。
4. 檢查最新研究方向、既有教授報告、研究筆記、實驗輸出、方法與限制；graph 和舊記憶只是線索，不能覆蓋較新的實際來源。
5. 清楚区分工作樹內容、已提交內容、remote-tracking 內容與已驗證公開內容。若只用 `git show` 讀到遠端提交，不稱已合併或已同步；記錄 commit 與來源路徑。
6. 每個關鍵數字核對原始結果檔的指標、單位、樣本數、切分與對照方法。保留失敗案例、無顯著差異與不支持的主張。
7. 查來源網站或 API 規格時，優先官方文件、原始論文、資料集及 repository。聲稱目前可用／不可用前要重新查證；歷史連線錯誤只寫成當時的測試紀錄。
8. 已封存的一次性研究只讀取最終產物，不為了補寫報告重跑。報告製作本身不授權新增實驗、改方法、採納新主張、合併、提交或推送。

來源台帳至少能回答：這句話來自哪個檔案／官方頁面、哪個版本／日期、支持到什麼範圍，以及有哪些尚未驗證的部分。可直接用報告內的來源連結與註解，不必新增重複的研究資料庫。

## 四、敘事主線：我的問題、判斷與研究進展

用以下順序串起可口頭敘述的研究故事，依本次資料增減篇幅：

1. 我想解決什麼問題，以及為何值得研究。
2. 我目前已經做到什麼；用少量重點先交代進度。
3. 我在哪裡遇到限制，原有資料或方法為何不足。
4. 我因此查找哪些資料、API 或模擬平台，如何縮小選項。
5. 我實際做了哪些驗證，得到了什麼正面或負面結果。
6. 我現在能下什麼結論，還不能宣稱什麼。
7. 我接下來要驗證什麼，以及想請教授討論的決策。

寫作要求：

- 使用繁體中文，語氣像使用者向教授報告，不是助手評分或指導使用者。
- 不用「建議你說」「這段值得報告」「你可以告訴教授」作為正文；直接寫可講出口的內容。
- 第一人稱不等於虛構經歷。不得編造搜尋順序、內心感受、實作經歷、硬體實驗或已完成的工作；來源不足就說明紀錄未確認。
- 區分「我查到平台支援」與「我已執行驗證」，「我預計採用」與「我已完成」；不能將工具功能寫成自己的實驗成果。
- 簡短解釋縮寫、指標與它們對研究的意義，不只堆疊實驗編號和數字。
- 區分估測準確度與控制效益、公開資料與實體部署；不把單一正向指標寫成整體優越性。

## 五、問題與 API 尋找過程的必要內容

### 問題紀錄

對每個會影響研究判斷的問題，交代「我遇到的現象 → 我如何定位 → 我採取的處理 → 結果與仍有限制」。

- 具體現象：資料缺口、格式／單位差異、樣本數不一致、API 連線失敗、執行環境相依性、不可識別模型、跨裝置失敗、噪聲或控制代價。
- 原因：區分已確認原因與仍在排查的假說，不能由錯誤訊息直接推導平台永久不可用。
- 處理：實際完成、嘗試但失敗、替代路線、尚待執行要分開。
- 研究意義：這個問題如何影響資料可信度、比較公平性、研究範圍或下一步。
- 主文講可理解的因果；完整錯誤訊息、版本與路徑放可展開區，僅保留必要資訊。

### API／平台探索紀錄

至少涵蓋以下問題：

1. 我需要模擬哪些物理量、擾動、感測與控制動作？需要什麼輸入、輸出和可重現性？
2. 我從哪裡找到候選：官方文件、論文、資料集頁、程式 repository 或既有研究筆記，附可追溯連結。
3. 候選究竟是靜態資料集、實體硬體介面、網路 REST API、模擬器，還是可本機執行的模型？不要全部統稱 API。
4. 我為何納入或排除：物理場景是否相符、是否可介入、是否支援所需變數／控制、取得與執行條件，以及基準是否適合。
5. 我實際驗證哪個端點、模型或版本，遇到哪些錯誤，如何轉向替代執行環境。
6. 本機模型跑通是否等於官方服務或 KPI 流程重現？若未驗證等價性，明確保留這個限制。
7. 最後採用、暫列候選、已排除與尚未評估的項目各是哪些；不把候選平台寫成已完成的研究路線。

可用小型比較表或探索時間線協助說明；只依有證據的先後順序排序。2026-09-14 範例包含 TCLab、BOPTEST、SECOM、OpenHumidistat，未來不必照抄這份候選清單。

## 六、證據邊界與教授受眾

- 分開呈現 synthetic full-field、real target-point、public task-aligned benchmark、intervention／causal evidence；一類成功不自動支持另一類。
- 提案、探索性模擬、正式確認實驗、已採納論文結果與未評估應用分開標示。
- 未做介入實驗，不宣稱真實控制效益或因果改善；未做硬體或跨設備驗證，不宣稱可直接部署。
- 保留失敗 run、代價增加、外推失敗、缺少資料及 `NOT_EVALUATED`，並說明它们如何改變我的下一步。
- 範例中的 E15 僅支持其公開同伺服器時間／負載轉移範圍，不擴張為桌機、NTC、完整空間場或因果控制證据。正式引用仍需讀 canonical 最終紀錄。
- 最新應用優先順序每次重新查來源；過往報告和 graph 的主題排列不是永久研究決策。
- 不加入無關個人開發、CI／Git 維護流水帳、工具使用數量或投稿行政。技術排查若直接解釋研究選擇與證據限制，則保留並轉成教授能理解的語言。

## 七、HTML 製作

1. 檔案放在 canonical thesis checkout 的 `docs/reports/`。新累積補報可沿用 `professor_catchup_report_YYYY-MM-DD_zh.html`；週報依既有命名。使用者要求修改時更新同一份，不另生多份近似成品。
2. 預設單檔、可離線閱讀：內嵌 CSS，不依賴 CDN、外部字型或網路圖片載入。引用連結可指向外部來源。
3. 使用語義標題、繁體中文語言標記、viewport、清楚的報告日期与涵蓋說明。
4. 開頭放少量研究摘要與章節導覽；主線清楚，細節和長來源可收在可展開區。
5. 包含可直接朗讀的第一人稱講稿與我想請教授討論的問題；若安排時間，各段加總須與預計時長一致。
6. 比較才用表格、過程才用時間線，不為裝飾增加圖；長表格局部橫向捲動，不能撐破整頁。
7. 本機來源優先相對連結。僅存在於遠端版本的來源用固定 commit 連結，並清楚標示，不做不存在的本機連結。
8. 不把 temporary QA scripts、使用者機器絕對路徑或工具私有快取路徑寫成可重用相依性。

## 八、驗證與交付檢查表

### 內容

- [ ] 正文與講稿都以「我」為主角，沒有助手指導口吻或捏造的經歷。
- [ ] 已涵蓋本次應補報的工作；沒有把文件存在當作已口頭報告。
- [ ] 問題、探索來源、比較理由、實際嘗試、失敗與下一步都有交代。
- [ ] 關鍵數字、日期、單位、樣本、對照與來源版本已核對。
- [ ] 歷史、最新、提案、探索、正式結果與未評估狀態沒有混用。
- [ ] 研究技術困難有保留；無關個人開發與投稿內容已排除。

### 檔案與畫面

- [ ] 在瀏覽器或可用的本機瀏覽器自動化中實際開啟 HTML；遵守適用 browser skill 和工具權限。
- [ ] 桌面、平板與手機視寬均檢查；本次範例為 1440、820、390 px，不是只看一張桌面截圖。
- [ ] 沒有整頁水平溢出、截斷文字、遮住內容的導覽或不可讀的表格；目視檢查長段落和比較表。
- [ ] 所有章節 ID 唯一、導覽錨點存在，展開／收合與鍵盤操作可用。
- [ ] 本機相對連結可解析；固定 commit 的來源路徑存在。不將唯讀查到的 repository 物件當作已公開可見。
- [ ] 阻擋網路載入時主體仍能閱讀；檢查 console 錯誤和外部資產相依性。
- [ ] 若本次要求列印或匯出，再檢查對應 print／PDF 版面；未測試就不宣稱通過。
- [ ] 執行範圍相符的檔案與 whitespace 檢查；新未追蹤檔也要納入，不能只看 `git diff`。
- [ ] 不為文件工作重跑研究實驗或修改科學主張；若另有這類變更，依專案流程另做 impact、verification 與 review。

### 交付

- [ ] 最後回覆提供實際 HTML 連結，簡述本次完成的重點，不只交出大綱。
- [ ] 驗證沒做到的地方與真正阻礙誠實註明；不要用檔案已生成代替畫面已檢查。
- [ ] 未經授權不額外 commit、push、合併或發布；本機完成與遠端公開分開報告。
- [ ] 若使用者本次要求保存流程，更新本記憶與索引；實際報告留在 thesis repository，不複製進 ResearchWorkspace。

## 九、沿用與更新

這份文件記錄的是製作流程，不是永久固定的 12 節模板、平台清單、研究結論或應用排序。之後的「一樣整理」「繼續」「以我為主角」應優先續作既有成果，再依最新要求調整。若使用者改變偏好，以最新明確要求為準；只有在要求更新專案記憶時，才把變動持久化到此處。

變更紀錄：2026-09-14 建立；納入第一人稱、累積補報、離線 HTML、研究問題與 API 探索過程，以及專案內持久保存的要求。澄清研究相關技術排查不受「排除無關工程流水帳」限制。
